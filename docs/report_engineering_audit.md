# OsdagBridge engineering report audit

The audited report is generated from the same 20 m, four-girder, 7.5 m carriageway example, with zero skew and a single-sided footpath. The reports committed before this audit are retained for comparison. [Original baseline](reports/Report_Before.pdf) · [Previous enhanced report](reports/Report_After.pdf) · [Audited report](reports/Report_Audited.pdf)

## Data flow and changes

| Area | Root cause | Change |
|---|---|---|
| Overall verdict | The executive summary combined a girder verdict with component maxima and never included the detailed grillage displacement checks. | `reports/design_results.py` structures the underlying checks by component, member, load case, demand, capacity, utilization, status, units, clause and source when available. The executive summary lists component verdicts, failures and availability warnings. A failed mandatory check governs even when other results are missing. |
| Girder identity | The capacity-check handler omitted the deck-overhang offset, so it counted the two edge-beam paths as primary girders. | `plategirderbridge.py` passes the same edge distance used by the results caches. `analysis_results.py` numbers the physical primary girders contiguously and keeps the edge-beam identifiers distinct. |
| Deflections | The detailed table used maximum absolute grillage nodal displacement. The summary took one stiffness-adjusted designer check with a lower demand. | The analysis, detailed design and executive sections share separate checked records for unfactored live load (L/800) and dead plus live load (L/600). The original designer checks retain their own provenance. `results_data.py` records the actual combination names with the displacement values. |
| Geometry and quantities | Chapter 2 assigned millimetre labels to post-design metre values. Chapter 5 repeated section properties from the controlling girder. | `report_utils.py` has explicit scale and precision formatting. `designer.py` records the section and calculated properties for each girder. Chapter 2 converts the stored SI dimensions once. Chapter 5 shows the section snapshot and uses per-girder check values for flexure and shear. |
| Initial and optimized bracing | The input table showed the seed sections. The capacity table showed the sections selected by the designer without explaining the difference. | Chapter 2 shows initial and design-selected sections per pair and check direction, with selection status. Chapter 5 reports the demand for the same pair and direction as the stored result. The report keeps Osdag's returned efficiency distinct from the ratio calculated using displayed member capacity. |
| End diaphragms | The original baseline reused cross-bracing rows. The current baseline already reports unavailable capacity on the sample. | The structured aggregation uses the dedicated end-diaphragm force and capacity data. The detailed and summary sections explicitly identify unavailable results. |
| Environmental inputs | A free-form cover location took precedence over the saved project location record. Computed wind and seismic forces were created by the solver but were missing from the report snapshot. | `reports/inputs.py` validates and resolves the recorded location fields. The pipeline records wind and seismic results where calculated and identifies solver defaults separately from site parameters. Wind setup reads the canonical UI keys with compatibility for the older aliases. |
| Presentation and drawings | Several tables contained empty cells, the reaction table had no data binding, and missing drawing boxes still received numbered captions. | The report uses availability text, repeating headers and right-aligned numerical columns in the revised result tables. It renders recorded support reactions. Existing desktop captures and optional offscreen CAD exports feed report images. A missing drawing receives an unavailable notice without a figure number. |

## Verification and remaining limitations

- Ran the complete repository test suite with `python -m pytest -q`. All 26 tests passed. Tests exercise mandatory failure propagation, fatigue, separate deflection criteria, units, bracing selection, missing inputs, diaphragm isolation, PDF compilation and drawing availability.
- Ran the design pipeline for the sample, compiled the audited report with two pdfLaTeX passes, checked page numbering and key numerical values, and inspected representative rendered pages. Compared extracted output with both retained baseline PDFs. This audit checks data flow, consistency and rendering. It does not independently certify structural calculations.
- **High — design compliance.** Sample fatigue and grillage deflection fail their reported checks. The report exposes those failures and the two deflection methods. Engineering review is required to determine the appropriate treatment of the stiffness-adjusted versus direct displacement methods.
- **High — missing diaphragm capacity.** The example produces no applicable stored end-diaphragm capacity result. The report shows `NOT EVALUATED`. The independent diaphragm retrieval is covered by regression tests using supplied result records.
- **Medium — environment configuration.** The recorded site wind speed and the solver's wind default differ. The sample has no explicit applied temperature load or horizontal road curvature calculation. Warnings identify missing context and documented defaults.
- **Medium — transverse-member efficiencies.** Some returned Osdag member efficiency values differ from the quotient of the separately reported axial force and member capacity. The report identifies their provenance. It does not infer the internal Osdag basis.
- **Medium — legacy tables.** Some older Chapter 5 classification, interaction and stiffener details still use shared designer report fields. The consolidated verdict and revised capacity tables use structured checks. Full clause and demand/capacity traceability depends on fields exposed by each solver, particularly for deck ratios and transverse members.
- **Low — CAD environment.** The cloud sample build did not have a generated pythonOCC model or desktop viewer captures. Unit tests cover rendering with an available drawing and with missing views. Actual desktop CAD rendering still requires a configured pythonOCC environment and a generated model.
